前一篇的 CSV 可以查到檢體編號、規則版本和資料完整截止日。有了這三類資訊，拿到兩份不同結果時就能依序追。先問兩次是否跑同一批輸入，再查截止日相不相同，最後比對兩次的規則。直接盯著百分比，通常看不出變動出在哪一步。

## 用固定的虛構輸入理解一次變動

例如覆核表提出調整某個配對條件。先固定示範檔、欄位對應與截止日，只在本機試算調整該條件。將兩次匯出的結果以示範檢體編號對照，檢查原先預期變動的個案有沒有改變，也挑幾筆預期維持原樣的資料一起確認。這種對照比只驗合計更容易發現例外條件被一併改動。

程式會保留每次比對使用的規則快照。網站預設規則更新後，已完成的工作結果仍有當時版本可供核對。覆核表上的建議要透過維護流程寫回規則檔，實際部署後，也要留意瀏覽器是否仍套用先前選過的本機設定。

## 把會影響結果的條件一併交接

| 交接內容 | 可回答的問題 |
| --- | --- |
| 示範輸入版本與欄位對應 | 兩次引擎收到的資料有沒有變 |
| 資料完整截止日 | 追蹤期滿狀態是否用了相同基準 |
| 規則快照與覆核狀態 | 當時套用了哪個版本的條件 |
| 資料檢查紀錄與逐筆輸出 | 哪一列被排除、提醒或重新分類 |

JSON 規則適合描述既有引擎支援的選項。若提出新的比對方式，還是要由工程師修改運算程式，先寫出新條件下的合成案例。表格審核負責把條件說清楚，測試負責確保程式照條件算，兩者要一起改。

在公開原始碼 `5c1ef82` 執行 `node scripts/check.mjs` 通過 23 項測試，涵蓋日期、欄位歧義、重複資料和規則快照等行為。這些結果只驗證軟體能依目前定義處理測試案例。示範規則要轉為單位採用版本，仍需完成專業覆核與資料使用審查。
