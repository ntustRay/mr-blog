AEO（Answer Engine Optimization，答案引擎優化）可以從一件具體的事開始：讓讀者提出一個問題後，能在文章中找到清楚、完整，而且有證據可查的回答。對技術部落格而言，這通常代表先交代結論與適用條件，再提供推導、範例與驗證方法。

本文採用這個工作定義，討論如何改善一篇文章的回答品質。搜尋結果是否顯示精選摘要、答案系統是否採用某個段落，仍需要另外觀察；不能從文章格式直接推定。

## 這篇的重點

- 一篇文章先回答一個主要問題，答案段落要連同適用條件一起讀才成立。
- 標題、正文、範例與參考來源應能互相核對；JSON-LD 補充頁面資訊，無法代替答案本身。
- 驗收分成內容可讀取、問題有被回答、搜尋平台實際如何呈現。前兩項可以在網站端檢查，第三項需要部署後的證據。

## 先把關鍵字改成讀者真的會問的問題

「Astro SEO」可以是一個研究主題，但還不足以決定一篇文章要回答什麼。「Astro 部署到 GitHub Pages 後，canonical 為什麼少了專案路徑？」就清楚得多：讀者遇到的是路徑問題，期待知道原因、修正位置，以及怎麼確認修好了。

寫作前先補完一句話：**讀完這篇，讀者能判斷或完成什麼？** 若答案同時包含選框架、部署網站、改善效能、申請廣告與評估 AI 引用，應先縮小範圍。把所有相關詞放進同一頁，會讓核心問題更難找到。

這裡也不需要為同一個問題生成十篇同義問句。讀者用「Pagefind 沒結果」或「Astro 搜尋壞了」進站，可能都需要同一份診斷；可以在一篇文章裡處理症狀差異，再連到真正不同的問題。

## 讓答案段落離開上下文後仍然成立

一個容易失去條件的回答是：「重新 build 就好了。」它省略了使用哪個搜尋工具、索引在哪個步驟產生，以及應該在哪裡驗證。讀者即使照做，也不容易知道自己的情況是否相同。

以這個部落格的 [`package.json`](https://github.com/ntustRay/mr-blog/blob/3bc18af4b516409c0d538d22805d4462c8d8f846/package.json) 為例，`build` 會依序執行 Astro 建置、`pagefind --site dist` 與內部連結檢查。若問題是「這個 Astro 專案可以只開 dev server 就驗證 Pagefind 搜尋嗎？」，可以先給這樣的回答：

> 在這個專案的設定中，Pagefind 索引由 `npm run build` 裡的 `pagefind --site dist` 產生。驗證搜尋時，先執行建置，再用 `npm run preview` 開啟產出的網站，確認查詢能回傳文章並正確導航。單看開發伺服器成功啟動，還不足以證明正式搜尋索引可用。

這段回答保留了主詞、設定範圍、操作順序與驗收結果。後面的正文再解釋為什麼要這樣做、如何查看錯誤，以及不同專案配置可能在哪裡分岔。這是根據此專案腳本整理的內容示例，沒有宣稱它曾被任何搜尋平台選為答案。

這種寫法同樣適用於技術比較。若問題是「什麼情況適合 DuckDB？」，答案應帶著資料位置、工作負載與限制；只留下「DuckDB 很快」，既不利於工程判斷，也容易在轉述後失真。

## 用標題安排推理，用來源限制主張

一篇排錯文章可以依讀者的判斷順序安排：先確認症狀，再解釋原因，最後給修正與驗證。每個 H2 對應一個可辨識的子問題，範例放在解釋附近，讓讀者不必來回尋找某個參數到底代表什麼。

定義適合用短段落；有明確先後關係的操作適合步驟；選項差異適合表格。選擇格式的理由是幫助理解，不需要把每一節都改成問答，也不必把完整論證切成許多只有一句話的區塊。

證據要靠近它支撐的句子。提到版本行為就連到對應的官方文件；引用測量數字就交代測試環境、工作負載與來源；根據資料提出建議時，說明哪些條件會改變建議。只在文末列一排連結，讀者仍可能不知道哪份來源支持哪個判斷。

作者與日期也有具體用途：讀者需要知道誰負責這份內容，以及它適用於哪個時間點。有實質修訂才更新修改日期，遇到未解的限制就保留限制，避免把歷史文章包裝成剛完成的新測試。

## Structured data 要描述實際存在的內容

這個網站的[文章模板](https://github.com/ntustRay/mr-blog/blob/3bc18af4b516409c0d538d22805d4462c8d8f846/src/pages/posts/%5Bid%5D.astro)使用 `BlogPosting` 描述文章，並提供 `BreadcrumbList`。驗收這類資料時，先逐項對照可見的標題、作者、圖片與日期，確認標記說的就是讀者看到的那篇文章。

能解析 JSON-LD，只能先證明這份資料具有可讀的語法；資料與頁面一致，才進一步證明它沒有描述錯內容。這兩個結果都無法直接證明搜尋平台會使用它，或在某種版位顯示文章。驗收報告應把這些結果分開。

也不要為每篇文章附上一份套版 FAQ JSON-LD。先確認頁面是否真的提供對應的問答，再查核目標平台當下支援的類型與適用條件。FAQ 的語法有效、符合特定呈現條件、被選為答案，是不同的判斷。增加標記應有明確用途，不必為了讓頁面看起來「做過 AEO」而增加另一份重複資料。

對這類內容網站，較容易落地的順序是：先確保正文可取得，再讓答案與證據能一起讀懂，最後補上符合頁面實況的標記。這是工程上的投入順序建議，沒有把某一種 metadata 當作可保證成效的排名訊號。

## 怎麼確認這次修改有用？

先在網站端確認三件事。第一，正式 URL 能取得預期的文章，重要內容不需要登入或使用者操作後才出現。第二，讀者只看標題、答案段落與一個範例，就能知道結論及適用條件。第三，頁面上的來源、作者、日期與 structured data 可以互相對照。

接著用一組固定問題觀察外部呈現。記錄查詢文字、日期、平台、地區或語言，以及文章是否出現、引用了哪一段、是否保留限制。如果有 Search Console 權限，再查看對應頁面和查詢的曝光與點擊變化。單次手動搜尋的截圖只能代表那次觀察，不足以證明穩定提升。

如果測試只是確認 `npm run build` 成功，就回報建置成功；如果看到文章被引用，就保留那次引用的證據。將結果分開，之後才有辦法判斷是網站仍無法被取得、文章沒有回答對問題，還是平台沒有選用它。
