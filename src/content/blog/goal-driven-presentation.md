技術簡報很容易照著開發過程寫：先介紹工具，再講架構，最後放成果。內容都有了，聽眾卻還是不知道這件事跟自己有什麼關係。

開始做 PPT 前，可以先寫一句話：**這場簡報結束後，希望誰理解什麼，或做出什麼決定？** 有了這句話，才知道哪些內容值得留下。

## 先寫清楚目標、對象與時間

同樣是介紹圖表效能，目標可以差很多。

| 條件 | 技術分享 | 改善提案 |
| --- | --- | --- |
| Target | 讓同事理解縮放為什麼會卡 | 讓主管決定是否投入改善 |
| Audience | 會維護圖表的工程師 | 需要分配人力的主管 |
| Time | 30 分鐘，含程式與討論 | 10 分鐘，保留決策時間 |
| 必要內容 | 問題重現、原因、程式差異 | 使用者影響、證據、成本與風險 |

上表是情境示例。同一份素材，放進不同會議，應該有不同的取捨。完整的實作細節可以放附件；會改變判斷的限制，則要留在主線。

## 用 4A 找出聽眾還缺什麼

4A 可以拿來檢查溝通走到哪裡：

| 階段 | 聽眾需要得到的答案 |
| --- | --- |
| Aware：知道 | 發生了什麼問題？ |
| Appreciate：理解 | 為什麼會發生，影響是什麼？ |
| Agree：認同 | 為什麼值得處理，方案有哪些取捨？ |
| Act：行動／決策 | 現在需要決定或執行什麼？ |

如果大家已經知道系統很慢，就不必花一半時間證明它很慢。真正缺的可能是改善範圍、需要多少人力，以及做完怎麼驗收。

這裡把 4A 當成檢查溝通缺口的方法，不要求簡報固定分成四段。純教學的目標可能停在理解與練習，也不需要硬塞一頁提案。

## 數據之後，要交代它代表什麼

放上 Benchmark 表格，只完成了資料呈現。DATA → INSIGHT → GO 可以幫忙接上後面的推理：

| 層次 | 要回答的問題 |
| --- | --- |
| DATA | 觀察到什麼？用什麼條件量到？ |
| INSIGHT | 這些資料支持什麼判斷？ |
| GO | 根據判斷，下一步要做什麼、怎麼檢核？ |

例如一頁標題只寫「效能測試結果」，讀者還要自己找結論。如果量測確實支持，可以改成「本次量測中，縮放延遲主要集中在重繪」。標題說明判斷，圖表提供依據，旁邊保留資料量、環境與量測方法。

但找到耗時位置，還不能直接推論某種改法一定有效。下一步可以是做一個限制範圍的 prototype，再用相同條件比較。沒有量測資料，就寫待驗證假設；只有資訊分享需求，也可以停在 DATA → INSIGHT。

## 每頁先有一句話，再決定怎麼排

先寫出這一頁要讓人理解的主要訊息，再選擇圖表、程式碼或架構圖。

例如要說明「資料查詢與繪圖各自負責什麼」，就把邊界、輸入與輸出畫清楚。若要比較兩個方案，則讓它們出現在同一個視野，保留相同的比較欄位。

「一頁一個主要訊息」可以協助聚焦，但不等於一頁只能放一張圖。把需要對照的內容拆到不同頁，反而可能更難理解。

排版時先區分重點、次重點與補充資料，再用字級、留白與顏色呈現層級。需要保留的風險與限制，也要讓人讀得到。

字體的分類、四款選擇與中英搭配，另外整理在[〈PPT 字體怎麼選？中文與英文的 4 款襯線、無襯線字體〉](../presentation-fonts/)。

## 讓 AI 先交 Storyboard

讓 AI 協助做簡報時，可以先要求它交出頁面規劃，檢查內容是否對準目標，再進入投影片製作。

```text
請先規劃簡報，暫不製作 PPT。

目標：讓團隊決定是否試行圖表效能改善。
對象：主管與前端工程師。
時間：10 分鐘，包含討論。
素材：以下貼上問題紀錄、量測結果與方案。

先指出缺少且會影響判斷的資料，再輸出：
頁次｜頁面目的｜主要訊息｜佐證素材｜呈現方式

依需求選用 4A 或 DATA → INSIGHT → GO，說明理由。
不要補造數字；區分事實、推論與待驗證假設。
保留會影響決策的風險與限制。
```

Review 時，先看每頁標題能否連成一條論述，再檢查證據是否支持主張，最後才調整視覺。若拿掉配色與動畫，仍然說不清楚要讓聽眾帶走什麼，就先回頭改內容。
